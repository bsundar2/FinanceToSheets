# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project does

Exports brokerage and bank account data to Google Sheets, plus marimo dashboards over it.

**SimpleFIN → Sheets** (`src/simplefin_to_sheets.py`) is the main pipeline, run on a schedule by GitHub Actions. It fetches balances for every account linked in a [SimpleFIN Bridge](https://beta-bridge.simplefin.org/) (checking, savings, credit cards, brokerages, 401k/IRA) and writes them all to a single `bank_accounts_dump` worksheet, plus any per-security holdings those accounts report to `holdings_dump`. It also rebuilds the Robinhood, Wells Fargo and Fidelity tabs from those holdings (`src/simplefin_portfolios.py`), so they refresh with no logins or file uploads. Which accounts show up is controlled entirely by what's linked in the Bridge, not by any code here. The one input that isn't from SimpleFIN is Fidelity's account-history CSV, fetched from Google Drive for YTD realized P&L (`src/fidelity_parser.py`). (The original Robinhood login + AWS Lambda pipeline and the local Fidelity positions CSV and Wells Fargo `.xls` parsers were removed once SimpleFIN covered those accounts; they're in the history of the archived private repo this one was moved from.)

`src/joint_account_ledger.py` is a second, related pipeline: it tracks each spouse's share of joint SimpleFIN-linked accounts at the transaction level, so the combined balance isn't attributed entirely to one person once both are contributing. See "Joint Account Ledger" below for the classification rules and known limitations.

`src/finance_dashboard.py` (the Yearly Overview page) and `src/net_worth_dashboard.py` (the Net Worth page) are two more marimo apps over the yearly budget spreadsheet - see "Personal finance dashboard" below.

`src/pnl_tracker.py` is a marimo app that computes YTD realized P&L from an uploaded Fidelity account-history CSV using FIFO cost-basis accounting, rendered as an interactive dashboard (best/worst trades, monthly view, per-ticker drill-down, weekly P&L vs. S&P 500 chart). Its FIFO matching and CSV parsing live in `src/pnl_calculator.py`, a shared, unit-tested module. Its S&P 500 benchmark fetch lives in `src/external_services/market_data.py`, also unit-tested.

## Fidelity account history via Google Drive

The account-history CSV only grows, past what fits in a GitHub Actions secret (~48-64 KB), so `src/external_services/google_drive.py` fetches it from a Drive folder shared with the same service account used for Sheets:

- **Setup**: create a Drive folder, share it with the service account's `client_email` (found in `data/gsheets_authentication.json`) with at least Viewer access, and set the `FIDELITY_DRIVE_FOLDER_ID` env var (or repo secret, for the GitHub Action) to that folder's ID (the segment after `/folders/` in its URL).
- **File naming**: anything containing `history` (case-insensitive), e.g. Fidelity's default `Accounts_History_2026.csv`. `sync_fidelity_account_history_from_drive()` downloads the most recently modified match, so old drops don't need to be deleted.
- **Fallback**: if `FIDELITY_DRIVE_FOLDER_ID` is unset, Drive fetching is skipped and `write_ytd_realized_pnl_to_sheets()` reads whatever's already at the local path. The file is optional, so a Drive failure is logged and skipped.

## Fidelity YTD realized P&L and dividends

The scheduled SimpleFIN run writes `fidelity_dump` (see "SimpleFIN → Sheets pipeline" below).

`write_ytd_realized_pnl_to_sheets()` runs after the position table is written: if `account_history.csv` was fetched, it computes YTD realized P&L with the same `src/pnl_calculator.py` engine the marimo dashboard uses, and writes it to fixed cells `fidelity_dump!L1` (label) and `fidelity_dump!M1` (value) — outside the position table's columns (A-J) so the cells stay put regardless of how many positions you hold. Reference `='fidelity_dump'!M1` from another tab to pull the figure in. No-op if the file isn't present. SimpleFIN's transactions can't replace this CSV for P&L: the Bridge returns only ~90 days of history, and trades carry a symbol and dollar amount but no quantity or price, so FIFO matching isn't possible. The CSV only needs re-uploading when you want this figure refreshed.

YTD dividends go in `fidelity_dump!L2`/`M2` - see the dividend ledger step under "SimpleFIN → Sheets pipeline".

## GitHub Actions: SimpleFIN export

`.github/workflows/simplefin_export.yml` runs on a schedule (~6am/2pm/10pm Pacific, plus ~9am/12pm Pacific on weekdays during market hours, when brokerages tend to refresh in SimpleFIN) as well as `workflow_dispatch`, with the same `GSHEETS_AUTH_JSON` secret restore/fail-fast step, and `SIMPLEFIN_ACCESS_URL` (required) and `HOUSEHOLD_CONFIG` passed through as env vars to `python -m src.simplefin_to_sheets`. `FIDELITY_DRIVE_FOLDER_ID` (optional) is passed too, only so `fidelity_dump`'s YTD realized P&L can still be computed from the account-history CSV. A manual run can tick the `preview` input, which sets `PORTFOLIO_TAB_SUFFIX=_preview` so the brokerage tabs are written as `<tab>_preview` (created automatically) for side-by-side comparison instead of replacing the live tabs; scheduled runs leave it empty. A second step then runs `python -m src.joint_account_ledger` with the same `SIMPLEFIN_ACCESS_URL` and `HOUSEHOLD_CONFIG` (joint account contribution ledger → `joint_account_ledger` - see "Joint Account Ledger" below). On a preview run it gets the same `PORTFOLIO_TAB_SUFFIX`, so it writes `joint_account_ledger_preview` (created automatically) and leaves the live tab, which the Budget sheet imports, alone. It still reads the live tab, since that's where the seed rows and overrides are.

It and `keepalive.yml` are the only scheduled workflows: `keepalive.yml` re-enables both once a month, since GitHub pauses a public repo's scheduled workflows after 60 days without activity (add any new scheduled workflow to its list). `python-tests.yml` runs `pytest` on pushes and pull requests.

## Joint Account Ledger

`src/joint_account_ledger.py` solves a specific problem: joint SimpleFIN-linked accounts (`JOINT_ACCOUNT_IDS`) were funded solely by one spouse so far, and the rest of this project's sheets have been treating their whole balance as that spouse's money. Once the other spouse starts contributing too, that stops being true - this pipeline computes each spouse's actual share from SimpleFIN transaction history instead of just splitting the current balance.

**Household config** (`src/household_config.py`): the accounts, matchers, start date and mortgage split identify the household, so they aren't in the code. They're read from the `HOUSEHOLD_CONFIG` env var (the JSON itself; a repo secret in Actions) or, locally, the gitignored `config/household.json`. `config/household.example.json` shows the keys, with made-up values, and the tests run against it (`tests/conftest.py`). The module reads it at import. Without accounts configured the export raises rather than writing an empty ledger. `prefer_available_balance_account_ids` in the same file is for `src/external_services/simplefin.py` (see `account_balance()`).

**Classification** (`classify_transaction()`): every transaction's SimpleFIN description is matched, in order, against:
1. `mortgage_matchers` (the mortgage's digits, or wording like "mortgage") → `"Mortgage"`: extra principal payments from a joint account are paid with your money, so the sheet counts them like `"Mine"` (they come out of your share), and also totals them in the summary's `My Extra Mortgage Principal Paid`. If the house is owned, say, 60/40, a Net Worth row of `-0.6 × mortgage balance` credits you only 60% of each extra payment; adding 0.4 × that total there credits the full amount. Checked before interest so "principal and interest" wording isn't split 50/50. The regular monthly autopay (`mortgage_autopay_matchers`, e.g. "AUTO PAY", on a mortgage match) is `"Mortgage Payment"` instead: it's split like the house, so `mortgage_payment_my_share_percent` of it comes out of your share and it stays out of that total.
2. `shared_bill_prefixes` (the start of the description of a recurring bill split 50/50, e.g. a phone bill or HOA dues and the payment processor's fee) → `"Shared"`: half the amount counts toward your totals. Checked before interest so a payee with "interest" in its name isn't mistaken for interest earned.
3. `_INTEREST_DESCRIPTION_PATTERN` (the word "interest", case-insensitive) → `"Interest"`, split 50/50.
4. `joint_account_matchers` (bare account-number digits or institution name identifying the *other* tracked joint account) → `"Joint Internal"` - money moving between the two tracked accounts isn't new money and must not be double-counted as a contribution on the receiving leg.
5. `personal_account_matchers` (bare account-number digits of accounts solely owned by you) or `my_payroll_matchers` (your employer's name on a payroll deposit split straight into a joint account) → `"Mine"`.
6. `spouse_matchers` (your spouse's employer on their payroll deposits, or their accounts' digits) → `"Spouse"`: $0 toward your totals, like `"Unclassified"`, but not counted as needing review.
7. Anything else → `"Unclassified"` - deliberately fails closed (excluded from your totals) rather than guessing, since an unrecognized source is exactly as likely to be your spouse's future contributions as it is a one-off wire transfer.

Matchers are bare digit sequences (e.g. `"1234"`, not `"XXXXXX1234"`) because different institutions mask account numbers differently in their transaction descriptions - e.g. `"XXXXXX1234"` at one, `"****1234"` at another. They're matched case-insensitively.

`Override Classification` also accepts a plain number instead of a label (e.g. `60`) for a one-off transaction that's a partial split rather than entirely yours or entirely excluded - e.g. a jointly-owed expense split 60/40, where the `My Contribution` formula computes `Amount * Override / 100`. `ISNUMBER()` in the sheet formula distinguishes this from the text labels.

**Tracking start date** (`start_date`, `LEDGER_START_DATE` in the code): both joint accounts were solely yours right up to this date, so instead of reconstructing history from SimpleFIN's limited transaction retention (observed: roughly the last couple months for these accounts), each account's balance *as of the end of this date* is captured once with a manual `SEED-<account-id>` row (`Transaction ID` not starting with `TRN-`, `Override Classification` = `Mine`, `Amount` = that account's balance at seed time) added directly to the sheet - see the archived repo's history for the one-off script used to create them. Two things enforce the cutover on every run: `build_ledger_df()` drops any existing row dated before `LEDGER_START_DATE`, and transactions are only ever fetched starting the day *after* it (fetching the seed date itself would double-count a same-day transaction that's already baked into the seeded balance). Moving the start date later requires re-seeding both rows with fresh balances.

**Manual review**: the `Override Classification` column is the only thing preserved across reruns - everything else is recomputed from the stored `Description` each run, so edits to the matcher lists apply retroactively without a backfill script. Set it on any `"Unclassified"` row (or to correct a misclassification, or to apply a partial-split percentage) to override `Effective Classification` for that row.

**Sheet layout** (`joint_account_ledger` tab), like the Stocks tab: a summary row at the top (labels in row 2, values in row 3, columns A-H, from `summary_cells()`): `Joint Balance Total`, `My Current Balance (Contributions + Interest)`, `Spouse Current Balance`, `Owed by Spouse (record in Splitwise)`, `My Contributions Total`, `My Interest Share Total`, `My Extra Mortgage Principal Paid`, `Unclassified $ Needing Review`. The transactions table has its header in `HEADER_ROW` (5) and rows from `FIRST_ROW` (6): `Transaction ID`, `Date`, `Account`, `Description`, `Amount`, `Suggested Classification`, `Override Classification`, plus formula columns `Effective Classification`, `My Contribution`, `Interest (Total)`, `My Interest Share` (A-K), then `Spouse Share`, `My Running Balance`, `Spouse Running Balance`, `Spouse Share Covered`, `Owed by Spouse (Splitwise)` (L-P, from `build_balance_columns_df()`, written by a second `write_to_sheets(..., start=(5, 12), clear=False)` call). The run reads the tab back with `read_from_sheets(..., header_label="Transaction ID")`, which finds the header row wherever it is (so a tab in the older layout, table from row 1, reads the same) and raises if the tab has content but no header, rather than rebuilding it from SimpleFIN's ~90 days and losing the seed rows and overrides. The Budget sheet's Net Worth tab reads the table by position, `IMPORTRANGE(..., "joint_account_ledger!C6:K")` for each joint account's `I`+`K` (your balance in it) and `B6:H` for extra principal, so moving the table means updating those formulas. Spouse Share is the part of each amount that isn't yours. The spouse's running balance never goes below zero: on a bill, their share is paid from their balance as far as it goes (`Spouse Share Covered`), and the rest, which your money paid, is `Owed by Spouse` - the one amount to record in Splitwise for that bill. Once it's in Splitwise it's a debt there rather than a negative balance here, so their later deposits stay theirs instead of paying it back a second time. My Running Balance is your contributions and interest less what they owe, so the two running balances add up to the joint balance; the summary's `My Current Balance` (which the Net Worth tab's per-account `I`+`K` sums match) still includes what they owe, and it minus `Owed by Spouse` is your money in the accounts. A bill the matchers don't know, like a property tax paid from a joint account, is Unclassified until its Override Classification is set, e.g. `60` for a 60/40 split. Unclassified rows count for neither of you until overridden. Runs automatically as the second step of `.github/workflows/simplefin_export.yml` (see "GitHub Actions: SimpleFIN export" above); can also be run manually with `python -m src.joint_account_ledger`.

## Architecture

### SimpleFIN → Sheets pipeline

```
src/simplefin_to_sheets.py
  ├── src/external_services/simplefin.py       # get_bank_accounts - raw SimpleFIN Bridge client
  ├── src/external_services/google_sheets.py   # write_to_sheets
  └── src/simplefin_portfolios.py              # brokerage tabs (column labels in src/constants/portfolio_columns.py)
```

**Data flow:**
1. `export_bank_accounts_to_sheets()` reads the `SIMPLEFIN_ACCESS_URL` env var; if unset, it logs an error and returns without writing anything (there's nothing to fetch without it). Otherwise it fetches the accounts once and builds both output tabs from that one response.
2. `get_bank_accounts()` in `src/external_services/simplefin.py` splits the Basic Auth credentials out of the Access URL (SimpleFIN embeds them as `https://user:pass@host/...` — `requests` won't send credentials left in the URL itself) and calls `GET {access_url}/accounts`. Any entries in the response's `errlist` (a per-account refresh failure, part of the SimpleFIN protocol) are logged as warnings rather than raised, since the rest of the account set is still usable.
3. `get_bank_accounts_as_df(accounts)` maps each account to `Institution` (`org.name`), `Account Name` (`name`), `Balance`, and `Balance As Of` (the `balance-date` unix timestamp converted to a date), skipping any account with no balance, sorted by Institution then Account Name.
4. Writes the result to a single `bank_accounts_dump` worksheet, covering every linked account regardless of type (checking, savings, credit card, 401k, IRA) — which accounts appear is controlled entirely by what's linked in the Bridge itself, not by anything in this codebase. Credit card balances come back negative (amount owed); any sign conversion needed to match a liabilities section elsewhere happens in the consuming spreadsheet formula, not here.
5. `get_holdings_as_df(accounts)` flattens each account's optional `holdings` list (a SimpleFIN field populated by some brokerages) into one row per security: Institution, Account Name, Symbol, Description, Shares, Market Value, `Cost Basis (raw)`, `Purchase Price (raw)`, Currency, As Of. Cost basis and purchase price are written unmodified because the protocol says `cost_basis` is per-share but some brokerages (reportedly Fidelity, Vanguard, Schwab, E*Trade) send total cost, and which convention each linked institution uses hasn't been confirmed. It logs one line per account with its institution and holdings count (or "no holdings field"), deliberately without account names, symbols or amounts, so a workflow run's logs show which institutions report holdings without exposing positions. Written to `holdings_dump` *after* `bank_accounts_dump`, so a holdings failure can't block the balances tab. `holdings_dump` is written with `write_to_sheets(..., create_if_missing=True)`, so unlike the other dump tabs it doesn't need to be created by hand; every other caller keeps the default of failing on a missing tab, so a typo'd tab name doesn't silently create a stray one.

6. `export_portfolios_to_sheets(accounts)` in `src/simplefin_portfolios.py` runs last and rebuilds the brokerage tabs in the same column layout as their original pipelines (`src/constants/portfolio_columns.py`). Accounts are routed by case-insensitive substring of org name and account name, not hard-coded account ids:
   - **Robinhood** (org contains "robinhood"): the account whose name contains "crypto" goes to `RH_crypto_dump`. The other Robinhood accounts' holdings are split into `RH_stock_dump`/`RH_etf_dump` by yfinance `quoteType`, and their balance minus holdings market value goes to `RH_cash_dump`.
   - **Wells Fargo** (org contains "wells fargo"): the account(s) reporting holdings are split into `WF_stock_dump`/`WF_etf_dump`, and the brokerage cash sweep account (`PREFER_AVAILABLE_BALANCE_ACCOUNT_IDS`) goes to `WF_cash_dump`. Both tabs add a `Dividend Portfolio` column (I) after the WellsTrade columns, for picking a dividend portfolio out of the brokerage: you tick it (a checkbox, or TRUE/yes/x typed in), and since the tabs are rewritten every run, `_ticked_symbols()` reads the ticked symbols back from the live tabs first and `build_wf_df()` writes TRUE for them again (blank for the rest). A failed read stops the Wells Fargo export instead of writing the tabs without the ticks. A ticked symbol that's sold drops off with its row.
   - **Fidelity** (org contains "fidelity"): only the account whose name contains "roth" goes to `fidelity_dump`, through `write_fidelity_positions_to_sheets()`, which re-applies the hand-entered stop prices (read back from the live tab by Symbol) and injects the R-multiple formulas (`R Value` = F-B, `Current R Multiple` = ((J/I)-F)/C, `Stop R Multiple` = (A-F)/C). YTD realized P&L is then fetched with `sync_fidelity_account_history_from_drive()` and written by `write_ytd_realized_pnl_to_sheets()`.

   **Dividend ledger** (`src/dividend_ledger.py`, run by `_export_dividends()` as the last step of `export_portfolios_to_sheets()`, after the brokerage tabs whose YTD cells it writes): SimpleFIN only returns ~90 days of transactions, so the main fetch asks for 90 days (`start-date`), and each run merges the dividends it finds into the persistent `dividends_ledger` tab (Transaction ID, Posted, Institution, Account Name, Security, Description, Amount, Symbol), keyed by transaction id. The table's header is in row 6 (`HEADER_ROW`), under a summary from `summary_cells()`: a column per account plus Total, with SUMIFS formulas for this year's dividends (row 3) and all time (row 4). The run reads the tab back with `read_from_sheets(..., header_label="Transaction ID")`, which finds the header wherever it is and drops blank rows. Symbol is the ticker, for totalling by ticker elsewhere (e.g. `SUMIFS(dividends_ledger!$G$7:$G, dividends_ledger!$H$7:$H, <ticker>, ...)`): Fidelity's Security already is one, and a Wells Fargo row is matched to the brokerage's current holdings by `match_symbol()`, word by word from the start of the name until one holding is left (WellsTrade abbreviates, e.g. `ACME WHSL CORP NEW COM` for `Acme Wholesale Corp`). A Symbol already in the tab is kept, so one typed by hand for a position since sold stays. Existing rows are never rewritten, and the history grows run over run. That also means a hand-added row survives, e.g. a one-off seed for dividends received before the ledger started (any unique Transaction ID, an Institution of `Wells Fargo` or `Fidelity`, and an Amount). Each institution describes dividends differently, so each has its own matcher:
   - **Wells Fargo** (`wells_fargo_dividend()`, only accounts with holdings, so checking/savings are never scanned): WellsTrade never says "dividend". A dividend is a positive amount whose description is `<SECURITY NAME> <MMDDYY pay date> <shares>` (e.g. `MICROSOFT CORP 100126 100` for +$25.00; the date is sometimes partly masked, as in `XXX426`), usually followed by an equal negative entry when it's reinvested. Cash sweep interest has the same shape (`BANK DEPOSIT SWEEP 093026 24`) and is excluded.
   - **Fidelity** (`fidelity_dividend()`, all Fidelity accounts): `DIVIDEND RECEIVED <name> (<SYMBOL>) (Cash)`. Amounts are stored as absolute values because SimpleFIN's signs for Fidelity flip partway through the history.

   Each institution's YTD total (this year's ledger rows) goes next to its positions: `WF_stock_dump!J1`/`K1` (outside the A-I table) and `fidelity_dump!L2`/`M2`. The ledger is read from the live tab even on preview runs. A failed read raises rather than reading as empty, so a transient error can't rewrite the ledger with only 90 days of rows.

   **Cost basis**: SimpleFIN's `cost_basis` comes back as 0 for these institutions, so `purchase_price` (per share) is used for every "Avg Price"/"Average Cost Basis" column. Robinhood crypto reports no `purchase_price` either, so any holding without one keeps the last known cost per share from the live tab (`_known_costs()`/`_with_known_costs()`; always the live tab, even on a preview run). Dead holdings are dropped (`_is_dead()`): $0 market value plus either 0 shares (a closed position SimpleFIN still reports) or no cost (e.g. an escrow placeholder like `ACME CORP ESC`, with shares but no value or cost). A real position missing a quote still has a cost, and Robinhood crypto has a value, so both are kept.

   **yfinance fills in what SimpleFIN doesn't carry** (`get_security_info()`/`get_dividend_history()` in `market_data.py`): ETF vs. stock, sector/industry/description, and `dividendRate`, falling back to the trailing 12 months of per-share dividends for ETFs, which don't report one. Wells Fargo's DVD Rate is the annual per-share dividend, and Est. Annual Yield is a fraction (0.0266 for 2.66%, as in the WellsTrade export) of the price implied by market value / shares. Robinhood's DVD Rate is annual / 4, the same quarterly normalization as before. The Robinhood received-dividend columns (Last Quarterly Dividend, Last Year's DVD, YTD DVD) are estimates: per-share dividends by ex-date times the *current* share count. Total DVD Paid (all-time) can't be derived and is left blank.

   **Failure handling**: a missing source account (e.g. a refresh failure dropped it) skips that tab rather than wiping it, and Wells Fargo's brokerage is identified by having holdings, so the same applies to a holdings-less glitch. If yfinance can't look up *any* symbol (Yahoo unreachable), the stock/ETF split raises instead of filing every ETF under stocks. Crypto and cash tabs are written first, since they don't depend on yfinance. Each institution runs independently; failures are logged and re-raised together at the end, so the workflow run shows red.

### Shared FIFO P&L engine (`src/pnl_calculator.py`)

- `parse_history()`: parses a Fidelity `Accounts_History_YYYY.csv` (path or raw bytes) into a clean DataFrame. Locates the "Run Date" header row dynamically (Fidelity prepends a variable number of preamble lines), cleans currency columns, and sorts chronologically — same-day ties sort buys before sells so same-day buy+sell pairs match correctly.
- `calculate_ytd_pnl()`: FIFO-matches `"YOU BOUGHT"`/`"YOU SOLD"` rows per symbol. Returns one entry per matched lot (a sale spanning multiple buy lots produces multiple entries), each with `symbol`, `buy_date`, `sell_date`, `qty`, `buy_price`, `sell_price`, `proceeds`, `cost`, `gain_loss`, `pct_gain`. Unmatched sells (bought before the history window) are returned separately as `missing_cost_basis`.
- Covered by `tests/test_pnl_calculator.py`. Not wired into the main pipeline.

### Interactive P&L dashboard (`src/pnl_tracker.py`)

A marimo app built on `src/pnl_calculator.py`: upload a Fidelity `Accounts_History_YYYY.csv` through the UI, and it renders realized P&L by ticker, best/worst trades by % gain, longest/shortest holds, a monthly breakdown, a per-ticker drill-down, and — as the final section — a weekly realized P&L chart benchmarked against the S&P 500. Excludes a fixed set of index-fund/cash-sweep tickers and non-standard symbols before matching. Run with `marimo run src/pnl_tracker.py`. The dashboard cells (upload parsing, tables) are not covered by the test suite; the weekly chart's data pipeline is covered indirectly via `tests/test_market_data.py`.

**Weekly P&L vs. S&P 500 chart**: realized P&L is bucketed into Friday-anchored weekly periods (`dt.to_period("W-FRI")`) and reindexed across every week of the trade year (~52-53 points), so weeks with no closed trades show as a zero bar rather than being omitted — this keeps the x-axis continuous and comparable week-to-week. `src/external_services/market_data.py`'s `get_sp500_weekly_returns()` fetches SPY weekly closes via `yfinance` (native `interval="1wk"` bars, indexed by each week's Monday) and computes week-over-week % returns keyed by the same `W-FRI` period, so it merges directly onto the realized-P&L series. This mirrors the approach the sibling `SwingTradeScreener` repo already relies on in production for its own SPY benchmark (`screener/screener.py`'s `download_histories()`), which handles Yahoo Finance's session/cookie requirements internally. Two alternatives were tried and rejected first: Stooq's CSV endpoint is gated behind a JS proof-of-work bot check a plain HTTP client can't solve (confirmed with and without a browser User-Agent), and FRED's daily SP500 series works but needed manual daily-to-weekly resampling that yfinance's native weekly bars avoid. On any fetch failure (e.g. no network access) it returns an empty DataFrame and the chart silently drops the S&P 500 overlay rather than failing the whole dashboard. The chart itself is hand-rolled inline SVG (bars for weekly $ P&L, a line for weekly S&P 500 % return on a shared zero-centered scale) rather than a charting library, consistent with the rest of the dashboard's hand-rolled HTML/CSS.

### Personal finance dashboard (`src/finance_dashboard.py`)

A marimo app over the yearly budget spreadsheet (`Budget - 2026`, overridable with the `BUDGET_SPREADSHEET_NAME` env var; it must be shared with the service account). Parsing and analysis live in `src/personal_finance.py` (unit-tested in `tests/test_personal_finance.py`), the same split as `pnl_calculator.py`/`pnl_tracker.py`; the notebook cells only draw. Those tabs are reports with title rows above their headers, so they're read as raw cell matrices with `read_values_from_sheets()` (unformatted values, dates as serial day numbers) and parsed by locating header rows and labels rather than fixed positions:
- **Expense Log** (Splitwise export): `My Owed` is your share of each expense, whoever paid. A household sheet's `Partner Expense Log` (read only if the tab exists, through `read_values_from_sheets()`'s optional tabs) is added in, so spending is the household's. Rows dated after today are skipped (Splitwise holds upcoming bills, like a property tax due next month), and rows at or above an adjustable threshold are listed separately as one-offs instead of charted. Above the monthly chart, a `finance_widgets.ShareBar` of each group's share of the year (with `allow_none`; it doubles as the chart's legend, and a group whose refunds outweigh its spending is a chip only) opens one group's sub-categories on demand: `monthly_by_category()` stacked by month with the group's total as a line, largest first and beyond eight summed into Other, plus a table with `budget_vs_actual()`'s figures for each, which count one-offs as the budget tables do.
- **Monthly Expenses**: each sub-category's group and monthly budget. Budget to date prorates the current month by day.
- **Savings by month**: the Yearly Overview's Saved tile and section 2 show the logged contributions (the Net Worth tab's Monthly Savings Contributions rows, below) in dollars, per month and year to date, not as a rate of take-home: an even twelfth of the yearly take-home skewed the rate in months the budget didn't match. They're logged savings, not take-home minus spending, so a purchase paid from savings, like a down payment, doesn't lower them.
- **Dashboard tab tiles**, split by topic: the Yearly Overview has income & savings and investment income (dividends, interest, stock gain/loss, market change) under its header KPIs, both drawn with `kpi_tile()`/`kpi_row()` from `finance_ui.py`. `parse_budget_items()` reads the Budget tab's `Total Gross Income`, `Take-Home Pay`, `401k Contribution`, `401k Company Match` and `Total Savings` rows by label, as (Actual Yearly, Budget Yearly); both the old sheet and the template use those labels. `parse_savings_log()` reads the older sheet's `Savings Log` tab (the Overview loads it with the other tabs, through `load_budget_workbook()`; it's optional, so the template, which has none, just skips those tiles) for `Dividends Received`, `Interest` and `Stock Gain/Loss` by the start of their column A label (the last is shown as "Realized gain/loss"). `market_change()` is the Dashboard tab's YTD Market Change: the net worth change less the logged contributions and the 401(k) plus match (which the contribution rows don't include), with its share of the change. It only counts contributions through the current month, so one logged early in a later month's column (the sheet's Q64 sums all twelve) makes the two differ by that amount. A tile whose row isn't found is left out.
- **Net Worth**: the subtotal rows and NET WORTH row for each month through the current one (later months only repeat the live current month), plus the Monthly Savings Contributions rows at the bottom, which split each month's change into what you put in and everything else.
  `contribution_buckets()` reads the Monthly Savings Contributions rows one by one (named like account rows, e.g. `Brokerage · Stocks`) for the Yearly Overview's **Savings by bucket** section, under Savings by month: those rows stacked by month with the month's total saved as a line, plus a month-by-bucket table. All-zero rows are dropped and, beyond eight, the smallest are summed into `Other`.
  `net_worth_breakdown()` also reads the account rows (label in column B) above each subtotal, for the Net Worth page (`src/net_worth_dashboard.py`, which reads just the Net Worth tab with `load_net_worth_tabs()`, since it shows current balances and leaves everything year-to-date to the Yearly Overview): the selected category's accounts stacked by month, with the subtotal as a line. Each account is named from its institution, account and type columns (D, B, C, e.g. `Wells Fargo · Savings · Joint`), since column B alone is often generic. A row whose account or type says liability, mortgage, loan, debt or credit card always counts as negative, because the live sheet keeps the mortgage positive and subtracts it in the Real Estate subtotal formula. Beyond seven accounts the smallest (by latest balance) are summed into `Other`, and any remaining gap between the rows and the subtotal shows as `Not itemized`, so the bars always add up to the subtotal.
  The Net Worth page opens on its **Allocation** overview, then drills into one category at a time instead of listing every category's details. The overview is the asset categories (`ASSET_COMPONENTS`: everything but Liabilities, with Real Estate net of the mortgage) as shares of their total in one 100% bar, plus `category_summary()`'s table (each category's value, share of assets, Liabilities included with no share). The bar is `finance_widgets.ShareBar`, an anywidget (hence the `anywidget` dependency) wrapped in `mo.ui.anywidget()`: clicking a segment, or its chip above the bar (Liabilities is a chip only), sets its `selected` trait, which re-runs the category panel below. It defaults to the largest category. It's drawn with flex divs, not an SVG, so it keeps its height on a phone, and its CSS lives in the widget, since anywidgets render in their own shadow root. The panel shows `allocation()`'s types for that category: its account rows grouped by the Type column (C: Stocks, ETF, Crypto, Foreign, I-Bonds, 401k, Roth IRA, Joint...) through `account_types()`, case- and space-insensitively, with the account's name standing in for a blank type, and a gap to the subtotal as a `Not itemized` type. They're drawn as a second `ShareBar` with `allow_none`, so clicking a type filters the holdings below to that type's accounts and clicking it again clears the filter. Shares are blank (`_weights()`) when a group mixes assets and debts, so Real Estate (house, mortgage) shows its rows but no bar and no filter. Below the types are the category's accounts stacked by month.
  Under the chart, a dropdown (All accounts, or one account, limited to the selected type's accounts) drills into row-level assets from `holdings_dump` (RH_Sheets, `load_holdings()`). `net_worth_accounts()` lists the rows with their Institution, Type, Balance Key and My Share % (the live sheet has neither of the last two, so no key and 100%). `holdings_accounts()` decides which SimpleFIN holdings accounts make up each row: with a Balance Key, every account whose `Institution Account Name` contains it (or a 4-digit number in it); without one, only Investments/Retirement rows are matched (so a brokerage's uninvested-cash row under Cash & Savings gets no securities), by institution, first the accounts whose name contains the row's type (`401k` matches `401(k)` once punctuation is dropped), then, if the row is the only one left for its institution, whatever accounts are left (Wells Fargo `Stocks` -> `WELLSTRADE`). `account_holdings()` merges a fund listed once per money source (Empower) into one row, scales by the share, and adds `Cash & other` for the rest of the row's balance. When the holdings are worth more than the row (usually the sheet's GOOGLEFINANCE prices vs. SimpleFIN's last close) there's no row for the difference, since it isn't a position, so such an account's rows add up to its holdings rather than its balance. A row with no holdings is one `Balance (no holdings reported)` row. Weights are blank when a category mixes assets and debts (house and mortgage). A failed holdings read is shown as a note and every account falls back to its balance.

Charts are hand-rolled SVG, like the P&L dashboard. The two notebooks share their `<style>` block (`STYLE`) and chart/table helpers (`stacked_bars_svg`, `table`, `fold`, `legend`, `money`, `PALETTE`) through `src/finance_ui.py`. Its service account credentials on Render are a secret file, found through the `GSHEETS_AUTH_FILE` env var (defaults to `data/gsheets_authentication.json`, so every other pipeline is unaffected). Setup steps are in `README.md`.

### One server for every dashboard (`src/dashboard_server.py`, `src/dashboard_nav.py`)

Render's `finance-dashboard` service runs `uvicorn --factory src.dashboard_server:create_app`, which mounts the finance dashboard at `/`, the Net Worth page at `/net-worth` and the P&L tracker at `/pnl` with `marimo.create_asgi_app()`, wrapped in `PasswordGate`. The old standalone `pnl-tracker` service is gone. The gate is used instead of marimo's own token login because, with several apps mounted, marimo keeps a separate cookie per app and redirects `/pnl`'s login to the root app's form, so `/pnl` could never be logged into. The gate: a `/login` page (password = `FINANCE_TOKEN`, compared with `hmac.compare_digest`, a 1s delay on a wrong guess), then one `itsdangerous`-signed, HttpOnly, SameSite=Lax cookie valid for every path for 1 day (the expiry is also enforced when the cookie is checked, not just by the browser). It's `Secure` when Render forwards `x-forwarded-proto: https`, and it's signed with a key derived from the password, so changing the password logs everyone out. Websockets without the cookie are closed with 1008. The `next` redirect only accepts same-site paths. `create_app()` refuses to start without a password. Covered by `tests/test_dashboard_server.py`.

`dashboard_nav.nav_html()` is the menu bar at the top of every notebook: Yearly Overview (`FINANCE_DASHBOARD_URL`, default `/`), Net Worth (`NET_WORTH_DASHBOARD_URL`, default `/net-worth`), Swing Trading (`PNL_DASHBOARD_URL`, default `/pnl`) and Spending (`SPENDING_DASHBOARD_URL`, SplitwiseToSheets's dashboard, hidden when unset). Swing Trading and Spending are separate apps with their own data, so their links carry an arrow-out-of-a-box icon (`_EXTERNAL_ICON`), unlike the two pages over the budget sheet. The icon is `display: inline-block`, since marimo's base CSS makes every `svg` a block, which would wrap it under the label. It has no third-party imports, because `pnl_tracker.py` also runs under Pyodide (html-wasm export), where the notebook imports it without the `src.` prefix.

Both dashboards share the dark styling of SplitwiseToSheets's spending dashboard. Each notebook's `<style>` block colors the page background, and `.marimo.toml` at the repo root (`[display] theme = "dark"`) makes marimo's own frame and widgets dark too. marimo finds that file by searching up from the working directory, so start the server from the repo root (Render does). Like the spending dashboard, each table sits in a `<details class="t-collapsible">` fold under its section title. The fold is closed by default, and its summary line shows a count and a headline figure. Charts and the P&L drill-down stay open.

The P&L tracker loads the newest `Accounts_History` CSV from the Fidelity Drive folder (`FIDELITY_DRIVE_FOLDER_ID`) through `fidelity_parser.latest_account_history_from_drive()` (`find_latest_matching_file()` + `download_file()` in `google_drive.py`). It shows the file's name and modified date, and an uploaded CSV takes priority. A Drive error is shown next to the upload widget instead of failing the page. In the html-wasm build the import fails and upload is the only source.

### Budget template (`src/budget_template.py`, `src/budget_migration.py`)

`build_workbook(BudgetSpec)` writes the yearly budget spreadsheet as an openpyxl `.xlsx` that gets imported into Google Sheets: the generic household template, one sheet both partners share (`python -m src.budget_template`), or an existing single-person sheet moved onto it (`python -m src.budget_migration <export.xlsx>`). There's no Sheets API step, since a newly created spreadsheet would be owned by the service account, which has no Drive storage. Tabs: Instructions, Settings (name/partner/year/each person's paychecks per year, at `Settings!B3:B7`, read by every formula), Income (each person's pay in their own four columns, C-F and H-K, rows 5-19), Budget (rows 5-19 add the two Income blocks up; category budgets below), Monthly Expenses, Expense Log and Partner Expense Log (SplitwiseToSheets's export columns, `My Owed` in column I; every SUMIFS adds both), Accounts (hand-entered balances in A:E, optional IMPORTRANGEs of each person's `bank_accounts_dump` spilling into G5:J and L5:O), Net Worth, and Dashboard. Row positions that depend on how many categories or accounts there are come from `plan_layout()`. Labels the dashboard parser matches (`Sub-Category`, `Budget Yearly`, `Monthly`, `Take-Home Pay`, the `Subtotal – ...` rows, `NET WORTH`, the contributions header and `Total Contributed (YTD)`) are kept verbatim, so `src/personal_finance.py` reads both layouts, and the household totals are what it sees.

The Net Worth design is what makes the household view work. Each row is one account at its full balance, with a Balance Key and each person's % (F, G; G defaults to `=1-F`). Its live months are `lookup_formula()`: an Accounts label exactly equal to the key + any imported account (either person's block) whose name contains it, e.g. `(1234)`, so rows don't break when SimpleFIN adds or reorders accounts. Subtotals are `SUMPRODUCT(month, F+G)`, so an ordinary row counts in full, and a row whose two %s cancel (Extra Principal Credit: the payer +40%, the other -40%) only moves equity between the two. The two rows under NET WORTH are `SUMPRODUCT(month, F)` and `SUMPRODUCT(month, G)` over the whole table: each person's net worth. All values are signed (the mortgage balance is negative). Top-5 lists on the Dashboard use LARGE/INDEX/MATCH (with an `Over Budget` helper column S on Monthly Expenses), not SORT/FILTER/QUERY, so Google Sheets, Excel and LibreOffice all evaluate them.

`migrate()` reads the old layout (Google's `.xlsx` export, with cached values) into your side of the household sheet:
- `unwrap()` undoes Google's `=IFERROR(__xludf.DUMMYFUNCTION("..."), cached)` wrapping of IMPORTRANGE/GOOGLEFINANCE/QUERY.
- Budget rows 5-19 are copied cell for cell into your Income columns. A category the old Total Expenses formula subtracted (`-C42`) becomes In Totals = No.
- Net Worth: the old rows held your share; the new ones hold the full balance. A live formula reading a fixed `'Savings Log'` cell becomes a Balance Key (the account's `(1234)` suffix, or the hand-entered label). A share factor (`=-0.6*'Savings Log'!...`, `=1555000*0.6`, `=0.4 * LET(...)`) becomes your % (`_share_factor()`), and frozen past values are divided by it; on an "Extra" row the partner's % is minus yours. Other formulas are moved with `translate()` (month columns +3, rows remapped, `COLUMN()-n` offsets adjusted, quoted text and other tabs untouched) at 100% yours. Rows the old Real Estate subtotal subtracted are stored negated.

`tests/test_budget_template.py` recalculates a built workbook in LibreOffice (skipped without `libreoffice-calc`) to check the formulas, and runs the dashboard parser over the result.

## Key conventions

- **Personal data stays out of the repo.** Account ids and digits, employer and payee names, and dates or splits that identify the household go in the household config, never in code, tests or docs. Test data is made up.
- **Logs**: Actions logs are public, so log counts and tab names, not account names, symbols, descriptions or amounts.

- **pandas `2.2.0`** is pinned in `requirements.txt`; upgrade it deliberately and run the tests.
- **Test suite**: `pytest tests/ -v` runs 295 tests across 15 files covering all major modules. Tests mock all external I/O (SimpleFIN, Google Sheets and Drive, yfinance). The spreadsheet formula tests recalculate in LibreOffice and are skipped without `libreoffice-calc`; `openpyxl` is in `requirements-dev.txt` for them and the budget template. Add `cffi` if `cryptography` raises a `PanicException` at import time in a new environment. To check a change end to end, run the SimpleFIN workflow manually with **preview** ticked.
